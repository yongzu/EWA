# PART 1. 기초 — 개념과 원리

## 1.1 메타프롬프트란 무엇인가

메타프롬프트는 특정 문제 하나의 답을 담은 프롬프트가 아니라, 답에 도달하는 절차를 담은 프롬프트다. 메타프롬프팅은 그 절차형 프롬프트를 만들고 활용하는 기법을 가리킨다.

일반적인 프롬프트는 "이 문제를 풀어줘"처럼 문제 하나에 대응한다. 메타프롬프트는 "이런 종류의 문제가 오면 항상 이 순서로 처리해줘"처럼 문제의 범주 전체에 대응한다. 문제의 세부 내용이 바뀌어도 절차는 그대로 유지된다.

## 1.2 두 가지로 쓰이는 이유

메타프롬프팅이라는 용어는 자료마다 가리키는 대상이 다르다.

**정의 A (구조 중심)**: LLM에게 문제 범주 전체에 재사용 가능한 절차형 템플릿을 주는 것. IBM의 설명과 Zhang 외(2023)의 논문이 이 정의를 쓴다. 내용(구체적 예시)이 아니라 구조(절차, 구문)에 초점이 있다.

**정의 B (도구 중심)**: LLM을 이용해 다른 프롬프트(또는 자기 자신의 프롬프트)를 생성·수정·평가하는 것. OpenAI 쿡북, GeeksforGeeks, PromptLayer 등 실무 자료 대부분이 이 정의를 쓴다.

두 정의는 충돌하지 않는다. A는 "완성된 템플릿 하나"를 가리키고, B는 "그 템플릿을 만드는 과정"을 가리킨다. 이 리포트는 두 정의를 모두 다루되, 어느 쪽을 말하는지 매번 표시한다.

## 1.3 메타프롬프팅이 작동하는 방식 (정의 A 기준)

IBM 자료는 이를 범주 이론과 유형 이론으로 설명한다.

- 작업의 범주(T)가 있다. 예: "예산을 배분하는 모든 문제".
- 구조화된 프롬프트의 범주(P)가 있다.
- 메타프롬프팅 함자(M)가 T의 각 작업을 논리 구조를 유지한 채 P의 프롬프트로 변환한다.

절차는 3단계다.

1. **작업 판단**: 개별 사례가 아니라 문제의 범주를 지정한다.
2. **구조화된 프롬프트로 매핑**: 순차적 절차 템플릿을 만든다. 사람이 직접 쓸 수도 있고 AI가 자동으로 생성할 수도 있다.
3. **실행**: 구체적 입력에 그 템플릿을 적용한다.

입력값이 바뀌어도 절차 자체는 바뀌지 않는다는 것이 핵심이다.

## 1.4 예시 1 — 역할 부여와 다단계 계산 (정의 A)

아래는 수학 방정식이 아니라 예산 배분이라는 일상적 계산 문제에 절차형 템플릿을 적용한 예시다.

**메타프롬프트**

```
너는 15년 경력의 개인 재무 코치다. 사용자가 월 소득을 알려주면 항상 아래 순서로 답한다.

1. 고정지출(주거비, 통신비, 보험료, 구독료)의 합계와 소득 대비 비율을 계산한다.
2. 남은 금액에서 변동지출(식비, 교통비, 여가비)의 적정 상한선을 소득의 30%로 계산한다.
3. 저축·투자로 배분할 금액을 소득의 20% 기준으로 계산한다.
4. 비상금이 월 생활비의 3~6배에 도달했는지 점검한다. 도달하지 못했다면 부족액을 계산한다.
5. 1~4의 계산 결과에 초과나 부족이 있으면 조정안을 제시한다.
6. 전체 결과를 한 문단으로 요약한다.
```

이 템플릿에 월 소득 300만 원을 입력하면, AI는 위 6단계를 순서대로 밟아 300만 원 기준의 숫자를 계산한다. 같은 템플릿에 월 소득 500만 원을 입력하면, 절차는 그대로 유지된 채 500만 원 기준의 숫자로 바뀐 결과가 나온다.

이 예시가 보여주는 것은 두 가지다.

- **역할 부여**: "15년 경력의 개인 재무 코치"라는 역할이 답변의 어조와 판단 기준을 고정한다.
- **다단계 계산**: 소득이라는 하나의 입력값이 고정지출 비율 계산, 변동지출 상한 계산, 저축액 계산, 비상금 점검이라는 여러 단계를 순서대로 거친다.

입력값(소득)이 T(작업 범주: 예산 배분 문제) 안의 한 사례이고, 위 6단계 템플릿이 P(구조화된 프롬프트)에 해당한다. 소득 숫자만 바꿔도 같은 절차가 재사용된다는 점이 일반 프롬프트와의 차이다.

## 1.5 예시 2 — 프롬프트를 만드는 프롬프트 (정의 B)

정의 B는 프롬프트 자체를 개선 대상으로 삼는다.

**원본 프롬프트**: "이 회의록을 요약해줘."

**메타프롬프트** (더 강한 모델에게 원본 프롬프트를 고치도록 지시):

```
아래 프롬프트를 더 명확하고 구조화되게 고쳐줘.
목적, 출력 형식, 분량 제한, 어조를 반드시 포함시켜.

원본 프롬프트: "이 회의록을 요약해줘."
```

**개선된 프롬프트** (메타프롬프트를 실행한 결과로 얻은 것):

```
다음 회의록을 읽고 (1) 결정 사항 (2) 담당자별 액션 아이템 (3) 다음 회의 일정을
표 형식으로, 300자 이내, 격식체로 정리해줘.
```

여기서 메타프롬프트는 최종 답(회의록 요약)을 직접 만들지 않는다. 최종 답을 만드는 데 쓰일 프롬프트를 대신 개선한다. 이 개선된 프롬프트를 실제 회의록에 적용하는 것이 다음 단계다.

## 1.6 메타프롬프팅의 세 가지 운용 방식

IBM 자료는 메타프롬프팅을 만드는 주체와 방식에 따라 세 가지로 나눈다.

- **사용자 제공 메타프롬프팅**: 사람이 직접 단계별 템플릿을 작성한다. 문제 해결 방법을 정확히 알고 있고 일관된 고품질 출력이 필요할 때 적합하다. 1.4의 예산 코치 예시가 여기 해당한다.
- **재귀 메타프롬프팅(RMP)**: LLM이 먼저 작업 설명을 받아 구조화된 프롬프트를 스스로 만들고, 그다음 그 프롬프트로 최종 답을 생성한다. 두 번의 패스로 이루어진다. 예제가 준비되지 않은 상황에 유용하지만, 첫 패스에서 만든 프롬프트의 품질에 따라 최종 결과가 좌우된다.
- **지휘자 모델 메타프롬프팅**: 여러 LLM 또는 AI 에이전트가 협업하는 구조다. 지휘자 역할의 모델이 큰 작업을 하위 작업으로 나누고, 각각을 전문 모델(산술 처리, 코드 작성, 결과 검증 등)에 맞는 프롬프트로 배분한다. 정확성과 적응성이 높아지지만 컴퓨팅 자원이 더 필요하다.

## 1.7 효과가 보고된 수치

IBM 자료가 인용한 실험 결과는 다음과 같다.

- 5,000개 경시대회 수준 수학 문제로 구성된 MATH 데이터셋에서, 제로샷 메타프롬프팅을 적용한 Qwen-72B가 46.3점을 기록했다. 이는 초기 GPT-4의 42.5점보다 높고, 파인튜닝된 모델의 성능도 앞선다.
- 코드 생성 작업에서 Python 전문가 역할을 메타프롬프팅 구조에 추가하자, 프로그래밍 퍼즐 성공률이 32.7%에서 45.8%로 올랐다.
- 셰익스피어 소네트 쓰기 작업에서 표준 프롬프트 대비 정확도가 62%에서 시작해, Python 해석기를 함께 사용했을 때 79.6%까지 올라갔다.

## 1.8 인접 개념과의 비교

| 기법 | 핵심 아이디어 | 메타프롬프팅과의 차이 |
|---|---|---|
| 제로샷 프롬프트 | 예시 없이 사전 학습에만 의존해 답한다 | 복잡한 작업에서 추론이 불안정해질 수 있다. 메타프롬프팅은 재사용 가능한 절차로 이를 보완한다 |
| 퓨샷 프롬프트 | 풀어놓은 예시 몇 개를 모방하게 한다 | 모델의 추론이 예시 내용에 종속된다. 메타프롬프팅은 예시가 아니라 절차 자체를 추상화해 특정 예시에 종속되지 않는다 |
| 생각의 연결고리(CoT) | "단계별로 생각해봐"라는 일반 지시로 순차적 추론을 유도한다 | 어떤 단계를 거쳐야 하는지는 모델 판단에 맡긴다. 메타프롬프팅은 그 작업 유형에서 정확히 어떤 단계를 거쳐야 하는지 미리 정의한다 |
| 생각의 나무(ToT) | 문제를 여러 "생각" 단위로 쪼개고, 여러 경로를 동시에 만들어 평가·탐색하며 막히면 되돌아간다 | CoT/ToT는 문제 하나를 푸는 동안의 사고 진행 방식을 다룬다. 메타프롬프팅은 그 진행 방식 자체를 문제 범주 전체에 재사용 가능한 틀로 만드는 것을 다룬다 |

생각의 나무(ToT)의 구성 요소는 다음 네 가지다.

- **생각 분해**: 문제를 다루기 적절한 크기의 단위("생각")로 나눈다.
- **생각 생성**: 같은 프롬프트로 여러 생각을 독립적으로 만드는 샘플링 방식, 또는 이전 생각을 기반으로 순차적으로 만드는 제안 방식을 쓴다.
- **상태 평가**: 각 생각에 점수를 매기는 값 평가, 또는 여러 후보 중 하나를 고르는 투표 평가를 쓴다.
- **검색 알고리즘**: 모든 가지를 각 단계마다 넓게 확인하는 너비 우선 탐색(BFS), 또는 한 가지를 끝까지 파고드는 깊이 우선 탐색(DFS)을 쓴다.

ToT는 스도쿠 퍼즐, 24 게임, 창의적 글쓰기, 미니 십자말풀이 등에서 성능 향상이 보고되었다. 다만 여러 경로를 유지하고 역추적하는 과정이 계산 자원을 많이 요구하고, 구현이 복잡하며, 가치가 낮은 경로까지 중복 탐색해 비효율이 생길 수 있다는 한계도 함께 보고된다.

# PART 2. 심화 — 최신 연구와 도구

## 2.1 두 개의 원류 논문

메타프롬프팅이라는 이름으로 독립적으로 발표된 논문이 두 편 있다. 이름은 같지만 방식이 다르다.

**Zhang, Yuan, Yao (2023), "Meta Prompting for AI Systems"** — 범주 이론과 유형 이론을 근거로, 작업 범주 전체에 적용 가능한 구조화된 템플릿을 제시하는 방식이다. 1부에서 설명한 정의 A가 이 논문을 바탕으로 한다. Qwen-72B를 이용한 실험에서 MATH, GSM8K, Game of 24 데이터셋에 대해 개선된 결과를 보고했다.

**Suzgun, Kalai (2024), "Meta-Prompting: Enhancing Language Models with Task-Agnostic Scaffolding"** — 하나의 언어모델을 다면적인 지휘자로 바꾸는 방식이다. 지휘자 역할의 모델이 복잡한 작업을 작은 하위 작업으로 쪼개고, 같은 모델의 서로 다른 인스턴스를 "전문가"로 호출해 각 하위 작업을 맡긴다. 지휘자는 전문가들의 출력을 통합하고, 자체 비판적 사고와 검증 과정을 거쳐 최종 결과를 다듬는다. Python 인터프리터 같은 외부 도구도 이 구조 안에 통합할 수 있다. 1부 1.6에서 설명한 "지휘자 모델 메타프롬프팅"이 이 논문에서 나온 개념이다.

두 논문 모두 IBM 자료의 각주로 인용되어 있으며, "메타프롬프팅"이라는 하나의 이름 아래 서로 다른 두 갈래(범주 기반 템플릿 vs. 지휘자-전문가 구조)가 존재한다는 점을 확인할 수 있다.

## 2.2 프롬프트 자동 최적화 계열

사람이 메타프롬프트를 직접 쓰는 대신, 알고리즘이 프롬프트 자체를 탐색·개선하는 연구들이다. 발표 순서대로 정리한다.

**APE, Automatic Prompt Engineer (Zhou 외, 2022)** — 지시문을 하나의 "프로그램"으로 보고, LLM이 제안한 후보 지시문들 가운데 점수 함수를 최대화하는 것을 탐색으로 찾는다. 24개 Instruction Induction 과제에서 사람이 직접 쓴 프롬프트(IQM 0.749)보다 높은 점수(IQM 0.810)를 기록했으며, BIG-Bench의 21개 과제 중 17개에서 사람 프롬프트와 비슷하거나 더 나은 성능을 보였다.

**OPRO, Optimization by PROmpting (Yang 외, 2023, Google DeepMind)** — LLM을 최적화 도구로 사용한다. 매 단계마다 이전에 생성한 해와 그 점수를 프롬프트에 포함시켜 다음 후보를 생성시키고, 이를 반복한다. 선형회귀나 외판원 문제 같은 일반 최적화 문제에도 적용되지만, 주된 응용은 프롬프트 최적화다. GSM8K에서 사람이 만든 프롬프트보다 최대 8%, BIG-Bench Hard 과제에서 최대 50% 높은 정확도를 기록했다. 이 과정에서 "Take a deep breath and work on this problem step-by-step"이라는 프롬프트가 자동으로 발견되어 화제가 되었다. 후속 연구(Zhang 외, 2024)는 130억 개 미만의 소규모 모델에서는 OPRO의 효과가 제한적이며, 이런 모델에는 "단계별로 생각해봐" 같은 단순 지시나 퓨샷 예시가 오히려 더 적합하다고 보고했다.

**PromptBreeder (Fernando 외, 2023, Google DeepMind)** — 유전 알고리즘으로 프롬프트 집단을 진화시킨다. 특이한 점은 작업용 프롬프트(task-prompt)뿐 아니라, 그 작업용 프롬프트를 변형시키는 변이용 프롬프트(mutation-prompt)까지 LLM 스스로 생성하고 개선한다는 것이다. 이를 "자기지시적 자기개선"이라 부른다. GSM8K 제로샷 실험에서 "SOLUTION"이라는 단순한 프롬프트가 83.9%를 기록해, OPRO가 찾은 80.2%를 넘어섰다. 프롬프트 하나의 표현 차이가 성능에 크게 영향을 미친다는 것을 보여준 사례로 인용된다.

**PE2, Prompt Engineering a Prompt Engineer (2023)** — 자동 프롬프트 최적화(APO) 계열에 속하며, 텍스트로 된 피드백을 명시적인 "그래디언트"처럼 다뤄 경사하강법과 비슷한 방식으로 프롬프트를 개선한다. OPRO가 일반적인 최적화 문제까지 다루는 것과 달리, 프롬프트 최적화 자체와 메타프롬프트 내부 구성요소 설계에 초점을 맞춘다.

## 2.3 자기 성찰·자기 수정 계열

LLM이 자기 자신의 출력을 스스로 비평하고 고치도록 만드는 기법들이다. 추가 학습 없이 추론 시점에서만 작동한다는 공통점이 있다.

**Self-Refine (Madaan 외, 2023)** — 하나의 LLM이 초기 출력을 생성하고, 같은 모델이 그 출력에 대한 피드백을 만들고, 다시 같은 모델이 그 피드백을 반영해 출력을 고치는 과정을 반복한다. 생성자·비평자·수정자를 모두 하나의 모델이 맡으며, 지도 학습 데이터나 추가 학습, 강화학습이 필요하지 않다. 대화 응답 생성부터 수학적 추론까지 7개 과제에서 평가한 결과, 일반적인 한 번의 생성 방식보다 평균 약 20%포인트 개선된 것으로 보고되었다.

**Reflexion (Shinn 외, 2023)** — "언어적 강화학습"이라 불린다. 환경에서 받은 이진 또는 스칼라 피드백을 텍스트 요약으로 바꾸고, 이를 다음 시도의 맥락에 추가한다. 모델 가중치를 업데이트하지 않고도 여러 번의 시행에 걸쳐 점진적으로 개선된다. HotPotQA에서 정확도가 약 20%포인트, HumanEval 코드 생성에서 pass@1 정확도가 약 11%포인트 개선된 것으로 보고되었다.

두 기법 모두 넓은 의미에서 메타프롬프팅과 맞닿아 있다. "어떻게 개선할 것인가"라는 절차 자체를 프롬프트 구조로 미리 설계해 둔다는 점에서 공통적이다.

## 2.4 실행 프레임워크: DSPy

DSPy는 스탠퍼드에서 개발한 오픈소스 프레임워크로, "프롬프팅이 아니라 프로그래밍"을 표방한다. 이름은 Declarative Self-improving Python의 약자다.

프롬프트 문자열을 사람이 직접 손으로 쓰는 대신, 입력과 출력을 선언하는 시그니처(signature)와 그 작업을 어떻게 풀 것인지 정의하는 모듈(module)로 프로그램을 구성한다. 그다음 MIPROv2 같은 옵티마이저가 평가 데이터를 기반으로 지시문과 예시를 자동으로 조정한다.

메타프롬프팅 관점에서 보면, DSPy는 사람이 메타프롬프트를 손으로 설계하는 대신, 옵티마이저가 데이터를 기반으로 최적의 지시문 구조를 탐색해 주는 접근이다. 2.2에서 다룬 자동 프롬프트 최적화 연구들의 아이디어가 실제 개발 프레임워크로 구현된 사례로 볼 수 있다.

## 2.5 알려진 한계

- OPRO는 130억 개 미만의 소규모 모델에서 효과가 떨어진다는 후속 연구가 있다. 이런 모델에는 단순한 직접 지시가 더 적합하다.
- 생각의 나무(ToT) 계열은 계산 비용이 크고 구현이 복잡하며, 가치가 낮은 경로까지 중복 탐색하는 비효율이 지적된다.
- 자기 수정(Self-Refine, Reflexion) 계열은 외부의 검증 가능한 신호(정답 확인 등) 없이는 모델이 스스로의 오류를 신뢰성 있게 고치지 못할 수 있다는 지적이 있다. 즉, 모델이 틀린 답을 "그럴듯하게 다시 틀리게" 고칠 위험이 있다.
- 프롬프트 자동 탐색 계열(APE, OPRO, PromptBreeder) 공통적으로, 자연어 프롬프트의 탐색 공간이 매우 넓어 전역 최적해를 찾았다는 보장이 없다는 한계가 있다.

# PART 3. 더 학습하면 좋을 자료

## 3.1 핵심 개념 용어집

- **프롬프트 엔지니어링**: LLM으로부터 원하는 출력을 이끌어내기 위해 입력(프롬프트)을 설계하는 작업 전반.
- **제로샷 프롬프트**: 예시 없이 지시만으로 작업을 수행하게 하는 방식.
- **원샷 / 퓨샷 프롬프트**: 하나 또는 여러 개의 풀어놓은 예시를 함께 제공하는 방식.
- **생각의 연결고리(Chain-of-Thought, CoT)**: 단계별로 생각하도록 유도해 추론 과정을 명시적으로 드러내는 방식.
- **생각의 나무(Tree-of-Thoughts, ToT)**: 하나의 경로가 아니라 여러 경로를 만들고 비교·탐색하는 방식.
- **인컨텍스트 러닝(In-Context Learning)**: 추가 학습 없이, 프롬프트 안에 제공된 정보만으로 모델이 작업을 수행하는 능력.
- **프롬프트 체이닝**: 하나의 작업을 여러 개의 프롬프트로 나누어 순차적으로 실행하는 방식.
- **프롬프트 튜닝**: 프롬프트에 해당하는 벡터(soft prompt)를 학습을 통해 최적화하는 방식. 프롬프트를 자연어로 다루는 프롬프트 엔지니어링과 구분된다.
- **프롬프트 최적화(자동)**: APE, OPRO, PromptBreeder처럼 알고리즘이 프롬프트 후보를 생성·평가·개선하는 과정 전체.
- **지휘자-전문가 구조(Conductor-Expert)**: 하나 또는 여러 모델이 지휘자와 전문가 역할을 나누어 맡아 복잡한 작업을 처리하는 구조.
- **자기 수정(Self-Correction / Self-Refine / Reflexion)**: 모델이 자기 출력에 대한 피드백을 스스로 만들고 반영해 결과를 개선하는 절차.
- **DSPy**: 프롬프트 문자열 대신 선언적 모듈로 LLM 파이프라인을 구성하고, 옵티마이저로 프롬프트를 자동 조정하는 프레임워크.
